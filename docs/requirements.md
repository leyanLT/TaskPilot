# TaskPilot V1.5 需求规格

- 文档版本：1.5
- 更新日期：2026-11-03
- 定位：单用户、本地优先的 AI 工作管理平台
- 增量说明：在 V1.0/V1.2 任务管理与 AI 确认机制之上扩展七个模块，不推翻已有技术栈、API 与数据。

## 1. 升级目标

1. 把任务管理扩展为项目管理：项目、归属、进度、归档、详情。
2. 让复杂任务可以拆成两级子任务，并统一完成规则。
3. AI 能基于真实数据拆解任务、建议优先级、安排每日计划、生成报告。
4. 新增应用内提醒、真实活动记录与可导出的进度报告。
5. 保持 V1.0 已有任务数据与 API 兼容；保持“AI 写入必须确认”的安全边界。
6. 保持单机、单用户、低运维；不引入消息队列、Redis、多 Agent 或全局状态库。

## 2. 角色与范围

- 单用户：无注册、登录、多租户或权限体系。
- 访问方式：浏览器页面，或通过自动生成的 OpenAPI 文档调用 API。
- 非目标：多人协作、公网 SaaS、邮件/短信/移动推送、跨设备同步、复杂日历集成、RAG、长期记忆、多 Agent、无限层级子任务、PDF/Word 排版引擎。

## 3. 术语

- **待确认操作（Pending Action）**：服务端持久化的 AI 写操作提案，包含唯一 ID、类型、载荷、状态、过期时间。
- **任务拆解草稿**：包含父任务、子任务、优先级、预计耗时、截止时间与执行顺序的可编辑提案；确认前不写任务表。
- **今日计划**：某本地日期下的时间块集合，每个时间块绑定真实待办任务。
- **派生提醒**：由真实任务截止时间与完成状态计算出的今日/即将截止/逾期提醒，可去重生成。
- **叶子任务**：没有子任务的任务；项目进度按叶子任务统计，父任务是容器，不重复计数。
- **报告事实**：后端根据数据库计算的结构化统计（时间段内完成、创建、逾期、项目进度、活动计数等）。

## 4. 功能需求

### F01 项目管理

字段：

| 字段 | 必填 | 规则 |
|---|---|---|
| ID | 系统 | UUID |
| 名称 | 是 | 1–100 字符 |
| 描述 | 否 | 最多 500 字符，空串保存为 null |
| 状态 | 是 | `planning` / `active` / `completed` / `archived`，默认 `planning` |
| 开始日期 | 否 | 本地日历日期 `YYYY-MM-DD` |
| 截止日期 | 否 | 不早于开始日期 |
| 创建/更新时间 | 系统 | UTC |

验收标准：

- 可创建、查看列表与详情、修改名称/描述/日期/状态。
- 可为任务设置所属项目；一个任务最多属于一个项目；任务可以没有项目。
- 项目详情展示基本信息、任务完成数量与比例、进行中与逾期任务、项目任务列表、最近活动。
- 进度由真实任务计算；无任务项目完成率为 0%，不出现除零或虚构百分比。
- 归档项目保留历史任务与活动；归档后不能向项目新增任务；可恢复到进行中。
- 项目及任务数据持久化，刷新与重启后保持一致。
- 项目统计口径为叶子任务（见 §3），并在项目详情、报告和文档中保持一致。

### F02 子任务与任务结构

验收标准：

- 可为已有顶层任务创建子任务；子任务默认继承父任务项目。
- 第一版只允许两级：父任务 → 子任务；子任务不能再拆分。
- 任务不能成为自己的子任务；服务端拒绝产生循环或更深层级。
- 子任务可独立编辑、完成、重开、删除、调整顺序。
- 父任务展示子任务完成数与进度；根据子任务完成情况计算。
- 父任务存在未完成子任务时，完成父任务返回 409 `TASK_HAS_UNFINISHED_SUBTASKS`，并说明剩余数量。
- 删除包含子任务的父任务时，服务端要求 `confirm_subtasks=true`，否则返回 409 `TASK_HAS_SUBTASKS` 并给出影响数量；界面二次确认文案同样指出会一并删除子任务。
- 子任务与普通任务共用 TaskService 的校验、活动记录、状态与时间规则，不重复实现。
- 子任务的所属项目跟随父任务；单独修改子任务项目被拒绝。

### F03 AI 智能任务拆解

用户场景：“我需要在两周内完成一个 AI Agent 项目，帮我拆解任务。”

Agent 应：

1. 理解目标与截止时间；必要时询问缺失信息（例如是否归属某个项目）。
2. 查询真实项目与任务作为上下文。
3. 生成可编辑的拆解草稿：任务标题、描述、所属项目、优先级、预计耗时、建议截止时间、子任务关系、推荐执行顺序。
4. 对不可实现或明显冲突的时间安排给出提示（项目已过截止、条目晚于项目截止、总耗时超过粗略剩余容量等）。
5. 展示草稿；用户可以编辑、删除、新增条目或子任务。
6. 只有用户确认后才批量写入；父任务与子任务在同一事务内创建。
7. 重复确认同一操作不会重复创建；取消不产生写入。

约束：

- 结构化输出必须经过后端 Pydantic 校验；非法数据返回可读错误。
- 不允许 AI 直接写数据库或绕过待确认操作。
- 不引入多个 Agent；不实现无限层级。
- 单次拆解最多 12 个父任务，每个父任务最多 8 个子任务。

### F04 智能优先级与每日任务规划

任务扩展字段：

- 优先级：`high` / `medium` / `low`，默认 `medium`。
- 预计耗时：5–1440 分钟，可空。
- 截止时间：沿用 V1.0 规则（带时区，存 UTC）。

优先级建议：

- 后端按以下因素确定性打分：用户设置的优先级、截止时间紧迫度、是否逾期、预计耗时、所属项目截止日期/状态、任务状态。
- 返回建议优先级、分数与可读理由；AI 负责解释，不得编造理由。
- 建议不会自动覆盖原优先级；用户确认（或点击采用建议）后才修改。
- 已完成任务不参与建议。

AI 每日规划场景：“我今天有 5 小时，帮我安排今天的任务。”

- 查询真实待完成任务、优先级、预计耗时、截止时间；识别逾期与紧急任务。
- 按可用时间生成时间块计划，包含开始/结束时间、任务、排序、理由。
- 允许用户确认或调整；确认后保存当日计划。
- 不得安排已完成任务；不得超出用户给的可用时间；时间块不得重叠；不得虚构任务。
- 缺失预计耗时时按 30 分钟估算并明确标注。
- 计划必须落在用户时区的当日；时间按 UTC 存储、按配置时区展示。
- 支持手动修改/移除时间块、取消整天计划；任务完成状态来自任务表。
- 不实现跨天自动重排或复杂日程优化。

### F05 提醒与通知

- 应用内提醒类型：今日待办、即将截止（默认截止前 24 小时）、逾期。
- 通知中心支持全部/未读筛选、已读/未读切换、全部已读、点击跳转对应任务。
- 已完成任务不再出现未完成类提醒；完成、截止时间变更后旧提醒会被清理。
- 相同提醒通过唯一 `dedupe_key` 去重，重复读取不重复生成。
- 提醒持久化，应用重启后已读状态保持一致。
- 不使用消息队列/分布式调度；不发送邮件、短信、移动端 Push；应用关闭后不主动通知。

### F06 进度跟踪与活动记录

- 记录任务创建时间、完成时间、状态变化、所属项目变化与关键字段修改。
- 记录项目创建、修改、状态变化。
- 展示项目最近活动与全局活动列表，可按项目/任务筛选。
- 活动记录必须在同一事务内随成功写入生成；写入失败不得产生成功记录。
- 活动是追加式日志：任务/项目被删除后仍保留快照标题与 ID，供报告追溯。
- 不实现分布式日志系统。

### F07 AI 日报与周报

支持每日工作总结、每周工作总结、项目进度报告。

数据规则：

- 报告必须有明确统计时间范围，并在正文中展示。
- “已完成工作”只来自 `completed_at` 落在统计范围内的任务，不得把当前状态直接等同于某时间段完成的工作。
- 统计（完成数、新建数、待办、逾期、项目进度、活动计数）全部由后端计算；AI 不参与数字计算。
- 没有数据时明确说明“没有已完成任务/没有逾期”，不得编造。
- 客观事实与 AI 建议分区展示；AI 只写“存在的问题/后续建议”。
- 报告内容应能追溯到任务/项目记录；事实 JSON 可随报告保存。

周报建议结构：本周工作概览、本周已完成工作、重点项目进度、未完成及延期事项、存在的问题、后续工作计划。
项目报告建议结构：项目基本信息、整体进度、已完成任务、当前待办任务、逾期及阻塞情况、后续工作建议。

功能：

- 生成草稿不自动保存；用户可预览、修改正文、保存、删除。
- 支持导出 Markdown。
- AI 未配置或调用失败时，报告仍生成确定性统计正文，并明确说明 AI 建议未生成。
- 不实现富文本编辑器、PDF/Word 排版引擎。

### F08 兼容与既有能力

- 保留 V1.0/V1.2 的任务 CRUD、筛选排序、逾期判断、AI 查询/创建/完成/编辑/删除/批量改期、持久对话、SSE 流式回复、服务端确认与幂等。
- 保留原有 API 路径与错误结构；新增字段为可选或带默认值。
- 保留原有任务数据；迁移不删除、不重建数据库。

## 5. 数据、事务与时间

- SQLite + SQLAlchemy + Alembic；新增表：`projects`、`task_activities`、`daily_plans`、`plan_items`、`notifications`、`reports`；`tasks` 增量扩展；`pending_actions` 扩展类型约束。
- 所有写入经过 Service；Repository 只做持久化；Agent 工具只调用 Service。
- 确认流程：“抢占 pending 操作 + 业务写入 + 标记 confirmed”在同一事务完成；失败整体回滚。
- 确认端点幂等；重复确认返回已保存结果，不重复创建任务/计划/报告。
- 任务拆解、今日计划、报告保存均支持确认前提交编辑后的载荷；载荷经后端 Schema 校验；非法载荷不消耗待确认操作。
- 时间统一 UTC 存储；计划日期、项目日期、报告范围按 `APP_TIMEZONE` 解释与展示；API 拒绝 naive datetime。
- 迁移前自动备份 SQLite 文件；提供恢复步骤；不删除或重建现有数据库。
- 数据库约束与 API Schema 双重校验关键规则（状态、优先级、耗时范围、层级、时间范围等）。

## 7. 前端页面要求

1. **Dashboard**：今日任务、即将截止、项目进度概览、今日计划、最近活动、未读提醒入口。
2. **My Tasks**：原有任务操作 + 优先级、预计耗时、项目筛选、子任务展开与操作、优先级建议。
3. **Projects**：项目列表、创建/编辑、归档/恢复、状态筛选。
4. **Project Detail**：基本信息、进度、任务列表、最近活动、编辑/归档。
5. **AI Assistant**：任务拆解、优先级、每日规划、报告；操作预览、可编辑草稿、确认。
6. **Calendar / Today**：今日计划、时间块、任务执行状态、日期导航、建议生成、手动增删。
7. **Reports**：日报/周报/项目报告生成、预览、保存、正文编辑、Markdown 导出。
8. **Notification Center**：即将截止/逾期/今日提醒、已读状态、跳转任务。

要求：

- 复用现有 Paper Day 视觉与既有表单/弹窗/列表组件；不重复实现。
- 加载、空状态、错误状态完整；桌面与基础移动端布局可用。
- 不引入不必要的 UI 框架或全局状态库。

## 8. 非功能需求

- **可用性**：AI 故障不影响任务、项目、子任务、计划、提醒与报告统计。
- **安全性**：本地单用户，默认仅监听本机；不提交真实密钥；日志不输出密钥；CORS 仅本地开发来源。
- **可维护性**：Service/Repository/Agent 职责分离；业务规则不重复；前端页面与组件分层清晰。
- **可测试性**：外部模型必须 Mock；数据库隔离；核心流程有回归测试。
- **可部署性**：Docker Compose 可启动前后端；SQLite 持久卷；迁移自动备份。
- **可观测性**：健康检查；服务端异常记录必要上下文但不泄露给客户端。

## 9. 验收边界与已知限制

- 无登录与权限系统，不能作为多用户公网服务。
- 仅一个持久对话；不提供多会话、长期记忆、RAG、多 Agent。
- 子任务仅两级；不支持无限层级或跨父任务移动。
- 每日计划为单日计划；不做跨天自动重排。
- 提醒仅应用内；无系统推送、邮件、短信。
- 报告为 Markdown 文本；无 PDF/Word 排版。
- 项目进度按叶子任务统计，与“任务总数”在不同页面可能有不同口径，文档与界面需明确。
- AI 回答质量依赖模型；自动化测试以 Mock 覆盖工具边界与确认边界，不代表真实模型质量。
- 真实 DeepSeek 未在 V1.5 回归中重新联调；详见验收报告。
